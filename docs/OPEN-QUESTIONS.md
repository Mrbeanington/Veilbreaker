# Open Questions

The source spec leaves these ambiguous. Each has a **proposed default** so work can proceed. The project owner may override any default; when that happens, record the change in DECISIONS.md.

| ID | Question | Proposed default |
|---|---|---|
| OQ-01 | **Simultaneous vs. alternating turns.** The spec asks for simultaneous planning but also wants "first-turn advantage" analytics, and classic team battlers alternate. | Build the resolver so both work: a `TurnModel` config with `simultaneous` (default) and `alternating`. Under simultaneous play, "first-turn advantage" is measured as the initiative-holder's advantage (OQ-02). |
| OQ-02 | Within the same resolution tier, whose action resolves first? | Initiative alternates each turn (a coin-flip seeded from RNG decides turn 1). Within a player, order follows the ally slot (1→3). Always deterministic and shown in the UI. |
| OQ-03 | Default energy generation. | 1 random energy per living character per turn, with a pool cap of 10 per type, full carryover, and no energy on turn 1 for the initiative player. All values configurable. |
| OQ-04 | Does life transfer (Borrowed Life) bypass anti-heal or "cannot be healed" (Behemoth)? | Healing has classes: `heal`, `lifeTransfer`, `setHp`. Anti-Heal and Behemoth's passive block `heal` only; Healing Reduction affects both `heal` and `lifeTransfer`. Log the decision. |
| OQ-05 | Legends are stronger and unlocked by accomplishment. How should they work in local ranked and friend matches? | Local ranked: bots in lower divisions use at most 1 Legend per team; the player may use any Legends they've unlocked. Friend matches: the host chooses "own unlocks" or "everything unlocked" with an optional max-1-Legend rule. Revisit at Phase 11 using simulation data. |
| OQ-06 | **Nameless One rewind semantics.** | When he would die, restore the full snapshot from the start of the current turn (both teams). The same actions do not replay; both players re-plan. The RNG stream advances (no identical re-roll). Once per battle, and consumed even if the rewound turn kills him again. |
| OQ-07 | Behavior when a Cheater changes targets "after selection" under simultaneous planning. | Implement retargeting as a Priority-tier effect that modifies queued actions, and log the change. |
| OQ-08 | Timer expiry with no lock-in. | Unlocked actions are dropped (character passes). In friend matches, the timer is advisory, since async turns have no shared clock; a player may resign or abandon. In local ranked against bots, the timer is optional in settings. |
| OQ-09 | Simultaneous team wipe. | Draw. In ranked, a draw counts as neither a win nor a loss, with a small MMR adjustment toward parity. |
| OQ-10 | **"MICHELIN MONSTER" uses a registered trademark.** | Rename before shipping (e.g., "The Five-Star Fiend", "Grand Kitchen Horror"). Use the placeholder id `chef-ramble.monster`. |
| OQ-11 | "Devourer of Worlds" has a well-known comic-book association. | Low risk as a generic phrase; flag it for legal review before launch. |
| OQ-12 | "Each culture must receive specific research before final visual production." Claude Code cannot substitute for cultural consultants. | Art specs are marked `status: draft`. Final production requires human review, ideally by people from those cultures. |
| OQ-13 | Hidden mechanics vs. ranked integrity. | Every effect that changes state emits a log event, even hidden ones; the event text may be cryptic but must exist. Codex entries unlock from the player's own event history. |
| OQ-14 | Maximum match length. | 40 turns; then the team with the higher total remaining HP percentage wins; if tied, draw. |
| OQ-15 | Mirror matches / duplicate characters. | No duplicates within a team; mirrors across teams are allowed. |
| OQ-16 | Players can edit local saves to unlock everything. | Accepted (ADR-002). Keep the checksum to detect accidental corruption only, and do not attempt obfuscation-based anti-cheat. |
| OQ-17 | Saves from older builds after balance/content changes. | Saves store IDs and progress, never character numbers. Migrations handle renamed or removed IDs. Every shipped BalanceVersion stays in the build for replays. |
| OQ-18 | Live WebRTC needs STUN/TURN servers to cross most home networks. | Stretch goal only, LAN-guaranteed. Public STUN is optional and off by default; code matches are the supported path. |
| OQ-19 | Browsers may evict IndexedDB data under storage pressure (especially Safari's ~7-day rule for non-installed sites). | The primary mitigation is installing as an app early, plus `storage.persist()`, rolling backups, and an easy QR transfer and share-sheet backup. |
| OQ-20 | Hosting. | Static host of the owner's choice. Also produce an optional single-file build for local/offline distribution. |
| OQ-21 | Art assets without an image API at runtime. | Art is produced offline from the CharacterArtSpecs and shipped as static, optimized images (WebP/AVIF) with lazy loading by region. Generated placeholder portraits are used until then. |
| OQ-22 | On iOS, installed home-screen apps have separate storage from Safari, and links/camera scans open Safari rather than the app. | Prompt install before real play; offer "Move my progress into the app"; iOS transfers use the in-app scanner or paste, not links. |
| OQ-23 | The transfer payload could outgrow a single QR code as content expands. | Budget ≤ 2,500 bytes compressed, tested against a maxed profile. The fallback is an animated multi-frame QR sequence, then the share-sheet file. |
| OQ-24 | A service-worker update could break an old save. | Migrations run before any save write in a new version, and the rolling backup is taken before migrating. |
| OQ-25 | Phase 00 requires zod schemas for `BattleState`, but full per-character runtime fields (HP, active statuses, cooldowns, live resource values) depend on the resolver design, which is explicitly out of scope for Phase 00. | Ship `BattleState` as a foundational skeleton now (format, teams, RNG state, energy pools, event log) and extend it with per-character runtime state in Phase 01 when the resolver is built. This is additive, not a breaking change, since Phase 00 ships no persisted battle states yet. |
| OQ-26 | ~~`apps/web/index.html`'s strict CSP meta tag was unverified against Vite's dev server (HMR websocket, eval-based dev tooling).~~ **Resolved 2026-09-17:** verified in the browser pane against both `vite dev` and `vite preview` (the production build) — the app renders, `document.title` updates to `GAME_TITLE`, HMR's websocket connects, and no CSP violations appear in the console. | No dev-only relaxation needed; the CSP as written works in both modes. |
| OQ-27 | OQ-01's `TurnModel` config has two values, `"simultaneous"` (default) and `"alternating"`, but Phase 01's `resolveTurn(state, actionsA, actionsB, deps)` only implements simultaneous resolution — it takes both players' actions together. | Deferred until a game mode actually needs alternating turns (see ADR-007). Building it speculatively now, with no content or mode to exercise it, risks guessing wrong about what "alternating" should mean operationally (does each side get a full resolveTurn cycle, or just action submission?). Revisit when local hotseat or a PvE encounter (spec/06) specifically calls for it. |
| OQ-28 | ~~OQ-09's "simultaneous team wipe → draw" rule and full win/loss detection from a team wipe were not implemented in Phase 01.~~ **Resolved 2026-09-18 (Phase 02):** `resolveTurn` checks both teams after every tier; a wipe on both sides emits `matchEndedInDraw`, a wipe on one side emits `matchEndedByTeamWipe`, and either takes precedence over the max-turn tiebreak for that turn. | Tested in `packages/engine/src/resolver.test.ts` ("simultaneous team wipe is a draw"). |
| OQ-29 | ~~13 statuses from spec/02's initial library had no concrete mechanic (Curse, Fear, Petrification, Mark, Stealth, Exposed, Resurrection Lock, Infection, Soul Consecration, Death Prevention), and 3 more (Energy Lock, Energy Cost Increase, Ability Lock) needed a per-application parameter the ActiveStatus model couldn't express.~~ **Further resolved 2026-09-18 (Phase 04, ADR-011):** Patient Zero needed Infection for real (just `tickBehavior: "damageOverTime"`, no new engine code) and Malachar needed Soul Consecration for real (a `hasStatus` check gating his Souls passive, plus a direct block in the `resurrect` effect handler). 6 remain data-only: Curse, Fear, Petrification, Mark, Stealth, Exposed. | Same disposition as before for the remaining 6 — full, valid, stackable, dispellable StatusDefinitions with a plain tooltip noting no mechanic yet, revisited when a real character kit (Phase 06+) needs one. |
| OQ-30 | The `drainEnergy` effect's `grantToSelf` path adds the drained amount to the source player's pool without checking `EnergyRules.poolCap` — `applyEffect` (packages/engine/src/effects.ts) has no `EnergyRules` in scope. | Left uncapped for now; no current ability exercises it. If a future ability needs the cap enforced on a granted steal, thread `EnergyRules` through `EffectContext` at that point rather than guessing the right plumbing today. |
| OQ-31 | Several Phase 03 trigger-system pieces are simplified pending real content: (a) ~~a passive/status's reactive effects always target the event's subject, never a resolved `TargetRule`~~ **partially resolved 2026-09-18 (Phase 04, ADR-011):** `Trigger.effectTarget: "self"` lets an effect land on the trigger's holder instead of the event's subject (Malachar's Souls passive needs exactly this) — but a full resolved `TargetRule` (e.g. a cross-character "thorns" mechanic targeting "whoever attacked me", a specific ally, or a random enemy) still isn't supported, only the binary subject-vs-holder choice; (b) `hasTag` and `secretScript` conditions always return `false` (no CharacterDefinition lookup is wired into the engine, and no secret script is registered) — still true, and now also the reason Malachar's Corpse Command can't literally borrow a defeated character's ability (see OQ-36); (c) `onMatchStart` is schema'd but never fired by `createBattle`; (d) `onTurnStart`/`onTurnEnd` fire once per living character at the literal start/end of `resolveTurn` — a reasonable reading, not the only one; (e) `onHpThreshold` re-fires on every qualifying `onDamaged` event rather than edge-detecting a single crossing, so a passive gated on it can fire repeatedly while HP stays below the threshold. | Kept simple until a real character's passive needs the richer behavior — see docs/DECISIONS.md ADR-010/ADR-011 for the reasoning on each. (a) is now half-done; a full per-reactive-effect `TargetRule` is the next piece, when a character actually needs to hit someone other than the subject or the holder. |
| OQ-32 | Summons: only `occupiesSlot: false` ("attached") summons do anything right now — they absorb damage for their owner. `occupiesSlot: true` ("temporary fourth unit") summons exist as tracked HP-bearing entities but aren't independently targetable, don't act, and don't count toward "living character" totals (energy generation, team-wipe checks). | Deferred until a real "fourth unit" character (Malachar-style, spec/03) forces the design — building full independent-unit integration speculatively risked getting the team-size-dependent mechanics (OQ-03's energy generation, OQ-09's wipe check) wrong without a concrete case to test against. |
| OQ-33 | A Transformation's `changes.tags` and `changes.energyCostOverrides` (packages/content/src/schemas/transformation.ts) aren't applied to runtime state by `applyTransformation` (packages/engine/src/transformations.ts) — nothing in the engine currently reads a per-character tag list or a per-character ability-cost override. | Apply them once something needs to read them: tags once `hasTag` gets a real CharacterDefinition lookup (OQ-31), cost overrides once `getEffectiveCost` (actions.ts) is extended to check a per-character override map alongside Energy Cost Increase. |
| OQ-34 | (Phase 04) `Transformation.trigger` (a `Condition`) is never automatically evaluated by anything in `packages/engine` — a character only actually transforms when an ability, passive, or status effect explicitly lists `{ kind: "transformInto", transformationId }`. Patient Zero's and Malachar's transformations both work today only because their kits deliberately check the same condition themselves (a passive for Patient Zero's automatic evolution; an explicit ability cast for Malachar's Death King). | Keep `Transformation.trigger` as accurate documentation of intent (and a value a future dev-tools/UI display could read) until a character design specifically needs the engine to auto-fire a transformation with no matching ability/passive effect to trigger it — building that speculatively risks guessing wrong about whether it should check every turn, every event, or something else. |
| OQ-35 | (Phase 04) `TargetRule`-based ability targeting can never select a dead character — `resolveTargets`' candidate pool (packages/engine/src/targeting.ts) always filters to `alive`. This blocks any real ability from casting `resurrect` at a chosen dead ally through the normal validate → resolveTargets → applyEffect pipeline; Phase 03's `resurrect` tests only exercise `applyEffect` directly with hand-supplied target ids, and Malachar's "You Belong to Me" was deliberately redesigned around a `summon` instead of `resurrect` specifically to avoid this (docs/design/characters/malachar.md). | Add an opt-in `TargetRule.includeDead` (or equivalent) flag once a real character's kit needs to cast a genuine "resurrect this specific ally" ability — most likely a healer/support Legend in a later phase. Not built speculatively now since no Phase 04 kit needs it. |
| OQ-36 | (Phase 04) The engine still can't target, or query the state of, one *specific* dead character: a Condition's `"enemy"`/`"ally"` target refs only ever resolve to a living character (packages/engine/src/conditions.ts), and per-effect `TargetRule` overrides only support `{ side: "self" }` (ADR-011) — ally/random/lowestHp/etc. per-effect targeting still isn't implemented, since it would need a `BattleState` + `RngState` threaded into `EffectContext` to re-run real targeting logic. Together these are why Malachar's Corpse Command, Raise the Forgotten, and You Belong to Me are all approximations rather than literal "use/raise/bind THIS corpse" mechanics (docs/design/characters/malachar.md). | Revisit once a character genuinely needs either: (a) per-effect targeting beyond self (e.g., a lifesteal-style ability that heals a *different* ally, not just the caster), or (b) real corpse-identity tracking (e.g., a character whose kit depends on "the last enemy who died" specifically). Both are more machinery than any Phase 04 acceptance criterion required. |
| OQ-37 | (Phase 05) `packages/ai/src/simple-bot.ts`'s `decideSimpleBotActions` guesses "lethal" from a flat sum of an ability's top-level `damage` effect amounts versus the target's current HP — no mitigation (damage reduction, shields, invulnerability) and no real simulation. Good enough for "random legal action, prefers kills" (phase-05-local-playable.md's own bar), not a foundation to extend for real bot levels. | Build `packages/ai`'s real BEGINNER/INTERMEDIATE/ADVANCED/EXPERT ladder from scratch in Phase 07, using `snapshotBattleState`/`restoreFromSnapshot` (packages/engine) to actually simulate a candidate action's outcome rather than guessing from raw ability data — this stopgap is not meant to be incrementally upgraded into that. |
| OQ-38 | (Phase 05) `apps/web` has no React error boundary — an uncaught exception anywhere in the component tree (a malformed prop, a future bug) blanks the whole app with only a browser-console stack trace, no in-app recovery. | Add one in Phase 08 ("Full client UI"), when there's a real navigation shell to fall back to (a "something went wrong — return home" screen) rather than the single-screen state machine Phase 05 built. |
| OQ-39 | (Phase 05) `SettingsContext` (animation speed, turn-timer on/off) is session-only React state — reloading the page resets both to their defaults. | Move into `packages/persistence`'s settings store once Phase 09 builds it; no local-save system exists yet for these to live in. |
