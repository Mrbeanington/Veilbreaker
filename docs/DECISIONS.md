# Architecture Decision Log

Format: `ADR-NNN — Title — Status (Proposed/Accepted/Superseded) — Date`, followed by Context / Decision / Consequences. Also register every custom character script here (see CLAUDE.md, rule 3).

## ADR-001 — Tech stack — Accepted (2026-09-17, Phase 00)
**Context:** The engine must be shared by the UI, bots, simulation, and friend-match verification. It must be deterministic, data-driven, and run entirely client-side (ADR-002).
**Decision:** pnpm TypeScript monorepo; pure `packages/engine` (integer math); `packages/content` with zod schemas; `packages/ai` (Web Workers + Node dev CLI); `packages/persistence` (IndexedDB); React + Vite static app; Vitest + Playwright.
**Consequences:** One engine codebase everywhere. The output is static files deployable to any static host. Confirmed unchanged during Phase 00 scaffolding; see ADR-003 for one addition (packages consumed as source, no per-package build step).

## ADR-003 — Workspace packages consumed as TypeScript source — Accepted (2026-09-17, Phase 00)
**Context:** `packages/engine`, `packages/content`, `packages/ai`, and `packages/persistence` are internal-only — nothing outside this monorepo ever imports them as published npm packages.
**Decision:** Each package's `package.json` points `main`/`types` at `src/index.ts` directly instead of a compiled `dist/`. `apps/web` (Vite) and Vitest consume that TypeScript source directly; each package's own `typecheck` script (`tsc --noEmit`) is the only place `tsc` runs on it. `apps/web` is the sole package with a real build step (`vite build`). Relative imports inside every package use extensionless specifiers (`./common`, not `./common.js`) — Vite/Vitest do not remap a `.js`-suffixed relative import back to its `.ts` source the way `tsc`'s `moduleResolution: bundler` would if the package were compiled to real `.js`, so extensionless imports are the form that resolves correctly everywhere (tsc, Vite, and Vitest) given this decision.
**Consequences:** Faster iteration (no build step between packages during Phases 00–08). No package here can be published standalone without adding a build step later — acceptable since none currently need to be.

## ADR-002 — Client-only platform — Accepted
**Context:** Owner requirement: no backend, no database, no server-side processing, no authentication requirement, and no external API dependency for core functionality.
**Decision:**
- Server authority is replaced by the local engine for solo play, and by commit-reveal plus deterministic replay verification for friend matches.
- The database is replaced by IndexedDB with versioned saves and export/import.
- Accounts are replaced by an automatic local profile.
- Online ranked is replaced by local ranked against bots.
- The admin panel is replaced by dev mode with exported balance files.
- Cross-player analytics are replaced by simulation reports plus personal stats.
**Consequences:** No global leaderboards, cross-device sync (except manual export), or tamper-proof unlocks. Friend matches are asynchronous by code; live P2P is optional. Hosting cost is effectively zero, and the game works offline.

## ADR-004 — Recursive zod schemas need a loosened Input type; the client-only guard exempts an audited vendor chunk — Accepted (2026-09-17, Phase 00 verification)
**Context:** Running the real Phase 00 acceptance criteria (`pnpm install && pnpm run ci`) after installing Node/pnpm surfaced two classes of bug the hand-review in the same session had missed.
**Decision:**
1. `effectSchema`, `randomOutcomeSchema`, and `randomOutcomeBranchSchema` (the mutually-recursive Effect/RandomOutcome types in `packages/content/src/schemas/effect.ts`) are annotated `z.ZodType<Output, z.ZodTypeDef, unknown>` instead of the single-argument `z.ZodType<Output>`. A single-argument annotation forces the schema's Input type to equal Output, but nested schemas with `.default()`-backed fields (e.g. `targetRuleSchema`) have an input shape strictly looser than their output shape, which real callers never notice because they always `.parse(value: unknown)`, never a value pre-typed as `Effect`. `exactOptionalPropertyTypes` was also dropped from `tsconfig.base.json` for the same family of reason (it does not compose with zod v3's `.optional()`/`.default()` output typing).
2. `apps/web/vite.config.ts` isolates React into its own `vendor` chunk (`build.rollupOptions.output.manualChunks`), and `scripts/verify-client-only.mjs` excludes that chunk from its external-URL/networking-API scan entirely (`VENDOR_CHUNK_PATTERN`). React's bundled internals contain strings that look like violations under naive scanning — W3C XML/SVG/MathML namespace URIs (DOM API identifiers, never fetched) and an inert `reactjs.org/docs/error-decoder.html` link embedded in minified error text — that have nothing to do with the app's own behavior. `apps/web/vite.config.ts` also sets `build.modulePreload: false`: Vite's default modulepreload polyfill contains a real (same-origin, harmless) `fetch(` call the guard can't statically distinguish from a call to a third party, and this single-entry Phase 00 app doesn't need the prefetch optimization it exists for.
**Consequences:** The client-only guard now enforces its rule against code this project actually writes, and treats a vendor dependency's internals as something to audit once by hand when added to `manualChunks.vendor`, not something to pattern-match on every CI run. Adding a new production dependency to the vendor chunk should get a one-time manual check that it doesn't call real network APIs.

## ADR-005 — EnergyPool is an explicit object schema, not an enum-keyed z.record — Accepted (2026-09-17, Phase 01)
**Context:** `packages/engine/src/energy.ts` needs a fully-required `{ MIGHT, FOCUS, SPIRIT, CHAOS }` type to read and write pool amounts without `?? 0` guards everywhere. `BattleState.energyPools` originally typed each player's pool as `z.record(energyFamilySchema, z.number())`.
**Decision:** zod v3 infers an enum-keyed `z.record`'s output as `Partial<Record<Family, number>>` (every key optional) rather than a fully-required record — real `tsc` output confirmed this the moment `packages/engine` tried to use it as a fully-required type. Added `energyPoolSchema` (a plain `z.object` with all four families required) to `packages/content/src/schemas/common.ts`, exported as `EnergyPool`, and used it for `BattleState.energyPools`'s value type (the outer map is still `z.record(idSchema, energyPoolSchema)`, keyed by playerId, which stays a proper `Record<string, EnergyPool>` since string-keyed records aren't downgraded to `Partial`).
**Consequences:** One canonical `EnergyPool` type, owned by content, used by the engine without defensive `?? 0` reads. General lesson for later phases: prefer `z.object` over `z.record(z.enum(...), ...)` whenever every enum member is genuinely always present.

## ADR-006 — Energy generation semantics: "fixed" mode and createBattle's turn-1 pass — Accepted (2026-09-17, Phase 01)
**Context:** spec/06's `EnergyRules.generation.mode` names `"random"` and `"fixed"` but only fully specifies `"random"` (OQ-03's default). Separately, the resolution order (spec/01) places "Resource generation" second-to-last (tier 14) and "Next turn" last (tier 15) — meaning a turn's generation really produces the *next* turn's energy, and turn 1 has no previous turn to have generated anything.
**Decision:** `"fixed"` mode grants every family `perLivingCharacter * livingCharacterCount` units directly, with no RNG draw — the simplest reading that still scales with team size the same way `"random"` mode's *total* unit count does, just without randomizing which family each unit lands in. `createBattle` (packages/engine/src/resolver.ts) runs one `generateEnergy` pass per team before returning the initial state, using the same `EnergyRules` the match will use, so OQ-03's "no energy on turn 1 for the initiative player" is meaningful (the non-initiative player actually has turn-1 energy) instead of vacuous (neither player would have any).
**Consequences:** `CreateBattleConfig` now requires `energyRules`, not just `matchFormat`. A caller must supply the *same* `EnergyRules` to `createBattle` and every subsequent `resolveTurn` call, or turn-1 energy and later turns' energy will be generated under inconsistent rules.

## ADR-007 — Resolver scope and cooldown timing (Phase 01) — Accepted (2026-09-17, Phase 01)
**Context:** phase-01-battle-core.md scopes the resolver to RNG, energy, action validation, and tier-ordered resolution — explicitly not the full combat/status/transformation systems (Phases 02–03).
**Decision:**
1. `packages/engine/src/effects.ts` (`applyEffect`) implements only `damage`, `heal`, `sequence`, and `randomOutcome` — enough to prove determinism and tier ordering end-to-end. Every other `Effect` kind throws a explicit "not implemented until a later phase" error rather than silently no-op'ing, so a future character definition can't accidentally depend on a mechanic (statuses, transformations, summons, resource/energy-modifying effects) that doesn't exist yet.
2. `Ability` gained an optional `resolutionTierId` field (`packages/content/src/schemas/ability.ts`); unset, the resolver defaults it to `STANDARD_RESOLUTION_TIER_ID` ("standard-attacks-support"). This is what makes "reordering the resolution-order config reorders events" (the phase's own acceptance criterion) meaningful to test at all.
3. Cooldown reduction (tier 13) explicitly skips any `characterId:abilityId` pair used during the *same* turn's action-resolution tiers. Reducing a freshly-set cooldown in the same pass would make `cooldown: N` only ever block `N-1` turns, since tier 13 runs later in the same turn as tier 6 where the ability was used and its cooldown was set.
4. The `death-checks` tier (10) marks `alive: false` and emits a `death` event, but does not determine a match winner from a team wipe (OQ-09's draw rule) — that belongs to Phase 02's "Death, resurrection, and death-adjacent rules". The only win-condition Phase 01 implements is OQ-14's max-turn HP-percentage tiebreak, since it was explicitly listed as a Phase 01 deliverable.
5. Only `turnModel: "simultaneous"` actually resolves (`resolveTurn(state, actionsA, actionsB, deps)` takes both players' actions together). `"alternating"` exists as a schema value (OQ-01) but has no resolver implementation yet — logged as a new open question rather than built speculatively ahead of any content that needs it.
**Consequences:** Phase 01's engine is real and tested, but a character/ability with a non-attack effect (a status, a transformation trigger, a summon) will throw at resolve time until Phase 02/03 extends `applyEffect`. That's intentional — it surfaces missing engine support immediately instead of a mechanic quietly doing nothing.

## ADR-008 — CI workflows let `packageManager` in package.json set the pnpm version — Accepted (2026-09-18)
**Context:** GitHub Actions CI had been failing since the very first Phase 00 push (both `ci.yml` and the new `deploy.yml`), silently — `pnpm run ci` was only ever verified locally, and no one checked Actions until setting up Pages surfaced it.
**Decision:** `pnpm/action-setup@v4` now refuses to run when both its own `version` input and `package.json`'s `packageManager: "pnpm@9.12.0"` field are set ("Multiple versions of pnpm specified"). Removed the `version: 9` input from both workflows; the action now reads the version from `packageManager` alone, which was already the source of truth locally.
**Consequences:** Local `pnpm run ci` passing is not sufficient evidence that GitHub Actions CI passes — check `gh run list` (or the Actions tab) after every push until this project has a habit of doing so automatically. This was two full phases (00 and 01) landing on `main` with red CI; nothing caught it because nothing looked.

## ADR-009 — Combat primitives: the status/damage/targeting model (Phase 02) — Accepted (2026-09-18)
**Context:** phase-02-combat-primitives.md needs a real status engine, a documented damage pipeline, and TargetRule evaluation (taunt, untargetable, random/lowest/highest-HP), landing on top of Phase 01's resolver.
**Decision, by subsystem:**
1. **ActiveStatus model** (`packages/content/src/schemas/battle.ts`): one record per `{characterId, statusId}`, with `stacks` (application count, capped at the definition's `maxStacks`) and `magnitude` (the most recent application's strength). Effective strength for any math is always `magnitude * stacks` — one rule, applied uniformly to Shield's absorption pool, Damage Reduction's flat reduction, a DoT/HoT's per-tick amount, and Damage Amplification/Weakness's modifier. A status without a numeric magnitude (Stun, Taunt, ...) just never has anyone read it.
2. **Stacking semantics** (`packages/engine/src/statuses.ts`, `applyStatusToCharacter`): `"none"` ignores a reapplication while active; `"refresh"` replaces duration and magnitude, keeps the stack count; `"stack"` adds a stack and replaces magnitude, duration untouched; `"stackAndRefresh"` does both. There is no per-stack independent expiry — all stacks of one status on one character share a single duration timer. Shield's absorption specifically collapses to a single stack at the reduced magnitude once damage consumes part of it (`setStatusMagnitude`), rather than trying to decrement across multiple stacked shield instances.
3. **Damage type table** (`packages/content/src/schemas/effect.ts` `DamageType` doc comment): normal runs the full pipeline; piercing skips only damage reduction and shield; affliction additionally skips invulnerable and reflect/counter, but amplification/weakness still applies to it (innate vulnerability, not defense). DoT ticks (Bleed/Burn/Poison) resolve as `"affliction"` — they're meant to punish reliably regardless of the target's defenses.
4. **Damage pipeline order** (`packages/engine/src/damage.ts`, `resolveDamage`): invulnerable → reflect/counter → amplification/weakness → damage reduction → shield → HP, exactly as phase-02-combat-primitives.md names it. Reflect fully redirects (target takes nothing, source takes the raw pre-mitigation amount, itself unmitigated to avoid reflect-loop recursion); Counter adds its own flat damage back at the attacker in addition to — not instead of — the target's own damage.
5. **Status duration exemption extended from ADR-006** (`decrementStatusDurations`'s `exemptStatusIds`): a status applied (or refreshed) in one tier of a turn is not decremented by that same turn's post-turn-effects tier, for the same reason a freshly-set cooldown isn't reduced by that turn's cooldown-reduction tier. Net effect: `durationTurns: N` means the status is active (and ticking, if it's a DoT/HoT) for the turn it's applied plus N further turns — N+1 total — mirroring how `cooldown: N` blocks exactly N turns after the one it's set on.
6. **Taunt redirects rather than rejects** (`packages/engine/src/targeting.ts`): when Taunt narrows the enemy-side candidate pool, an explicit `scope: "single"` selection outside that pool is silently redirected to the taunter(s), not treated as an illegal-target error. Treating it as an error would make a taunting tank's team immune to single-target attacks entirely, which defeats the entire point of Taunt.
7. **Cooldown Increase/Reduction** (resolver.ts's cooldown-reduction tier): net decrement per turn = `max(0, 1 + reductionMagnitude - increaseMagnitude)`, still exempting cooldowns just set this same turn.
8. **Deferred statuses**: beyond spec/06's own three (Infection, Soul Consecration, Death Prevention), nine more ship as fully valid, applicable, stackable, dispellable StatusDefinitions with no unique engine hook yet: Curse, Fear, Petrification, Mark, Stealth, Exposed, Resurrection Lock (spec never defines a concrete mechanic for these), and Energy Lock, Energy Cost Increase, Ability Lock (each needs a per-application parameter — which family, which ability — that the single-`magnitude` ActiveStatus model can't express without a real character forcing the design). Logged as OQ-29.
9. **`drainEnergy`'s grant-to-self is uncapped**: `applyEffect` has no `EnergyRules` in scope to check the pool cap against. Logged as OQ-30 rather than threading `EnergyRules` through the whole effect pipeline for one edge case with no character exercising it yet.
**Consequences:** The 19 statuses phase-02-combat-primitives.md's acceptance criteria actually exercise (Stun, Silence, Invulnerable, Untargetable, Damage Reduction, Shield, Counter, Reflect, Bleed, Burn, Poison, Anti-Heal, Healing Reduction, Healing Amplification, Cooldown Increase, Cooldown Reduction, Taunt, Damage Amplification, Weakness) are real and tested end to end. The remaining 13 are honest placeholders, not silent no-ops — nothing pretends they do something they don't.

## ADR-010 — Advanced systems: triggers, transformations, summons, death extensions, RNG manipulation, Cheater hooks (Phase 03) — Accepted (2026-09-18)
**Context:** phase-03-advanced-systems.md is the largest single phase so far: an event-driven trigger/passive engine, the transformation and summon systems, death prevention/erasure/resurrection, state snapshots, and every remaining spec/01 RNG-manipulation and Cheater mechanic. Every design choice below is the "simplest option that keeps the system reusable" for an ambiguity the spec left open, per CLAUDE.md's session protocol — none were destructive/irreversible, so none blocked on a question back to the project owner.
**Decision, by subsystem:**
1. **New `PassiveDefinition`** (`packages/content/src/schemas/passive.ts`): a standalone `{trigger, condition?, effects}` bundle, referenced by `CharacterRuntimeState.passiveId` (itself new — swappable by a Transformation's `changes.passiveId`). Spec/02 describes reactive hooks living on statuses (`StatusDefinition.triggerTiming`, already schema'd in Phase 00) but never names an equivalent for a character's own passive; without one, "Triggers and Conditions" would have nothing but statuses to attach to.
2. **One trigger evaluator for both passives and statuses** (`packages/engine/src/triggers.ts`, `evaluateEvent`): every living character is scanned each event for (a) its current passive and (b) each active status's `triggerTiming`, using the same `Trigger` (`event` + new `relation` field + optional `condition`) and the same `evaluateCondition` (`conditions.ts`, new). `relation: "self" | "ally" | "enemy" | "any"` is what makes "onDeath (any/ally/enemy)" concrete — computed from whether the trigger holder and the event's subject share a team.
3. **Trigger-fired effects always target the event's subject** (`targetIds: [gameEvent.subjectId]`), not a resolved `TargetRule` — a passive/status's effects aren't wrapped in an ability with its own targeting, and building a second targeting path for reactive effects was more machinery than any acceptance criterion needed. A caught test bug (a "thorns" fixture assuming it could hit "whoever attacked me") is the concrete evidence this would have silently done the wrong thing — logged as OQ-31 rather than building real reactive targeting speculatively.
4. **Recursion guard, `MAX_TRIGGER_DEPTH = 5`** (`triggers.ts`): a trigger's own effects can produce events that fire more triggers (a passive that deals damage is itself an onDamaged/onDamageDealt event); depth-capped rather than left to recurse, logging `recursionGuardTripped` and stopping. Verified with a genuinely self-perpetuating fixture (a "when damaged, take 1 more damage" passive) rather than a contrived two-character loop, since passive effects target the event subject (point 3) — a cross-character ping-pong needs real attacker-targeting this phase doesn't have.
5. **Erasure is a distinct event, not just fatal damage** (`effects.ts`'s `erase` kind, emitting `"erased"`): `deriveGameEvents` (triggers.ts) maps a `"death"` AppliedEvent to `onDeath`/`onKill`, but never maps `"erased"` to anything — that omission alone is the entire mechanism behind spec/02's "erasure that bypasses death triggers" (Shiro). `resolver.ts`'s death-checks tier only marks a character dead (and only then emits `"death"`) when it *finds* one at ≤0 HP with `alive` still `true`; `erase` already set `alive: false` directly, so that tier silently skips them.
6. **Kill attribution via a same-turn "last damager" map** (`resolver.ts`'s `lastDamageSourceByTarget`): `"death"` itself carries no attacker, so a transient per-turn `Map<targetId, sourceId>` (updated on every `"damageDealt"` event) supplies the death event's `sourceId`, which `deriveGameEvents` uses for `onKill`'s subject. Reset every turn — a kill only credits whoever landed the *most recent* hit this turn, not a full damage-contribution ledger.
7. **Death Prevention floors at 1 HP and self-consumes** (`damage.ts`'s `applyHp`): a save is single-use per application, matching OQ-06's "consumed even if the rewound turn kills again" pattern reused here for consistency, and floors rather than fully blocking (Aurelia "cannot fall below 1 HP", not "cannot be damaged").
8. **Summons: attached (non-slot) ones absorb, slot-occupying ones don't** (`summons.ts`, `damage.ts`): `Summon.occupiesSlot: false` (attached summons, spec/06's "absorption counters") makes `resolveDamage` redirect damage meant for the owner into the summon's own HP first, with overflow beyond its remaining HP continuing into the owner's own pipeline; `occupiesSlot: true` ("temporary fourth unit") summons don't intercept anything, since full independent targeting for a fourth unit is a larger feature no acceptance criterion needed yet (logged as OQ-32). `instanceId` is derived deterministically from `(owner, summonId, existing-count)`, not a module-level counter or a fresh RNG draw — CLAUDE.md rule 4 bans hidden mutation, and a counter living outside `BattleState` would make identical calls from different states collide or diverge.
9. **Transformation preserves statuses by never touching them, and rescales current HP by ratio** (`transformations.ts`): `changes.maxHp`, if present, scales current HP by `newMax/oldMax` rather than leaving the absolute number (a "weakened" stage would otherwise leave a character disproportionately tanky) or fully healing (a free heal an evolution shouldn't grant outright). `changes.tags` and `changes.energyCostOverrides` aren't applied to runtime state yet — nothing reads a per-character tag list or cost override today (logged as OQ-33).
10. **RNG manipulation as a one-shot queued modifier, consumed by the next `randomOutcome` roll** (`rng-modifiers.ts`, `ActiveStatus`-adjacent `RngModifier` on `CharacterRuntimeState.pendingRngModifiers`): spec/01 names four manipulations — force outcome, guarantee min/max, reroll, weight modification — all "implemented as modifiers on RandomOutcome" per phase-03-advanced-systems.md. Since a `RandomOutcome` branch carries only a weight (no inherent numeric value), "min"/"max" are read as author-order convention: branches are listed worst to best, and `guaranteeMin`/`guaranteeMax` pick the first/last. `weightBoost` multiplies the last branch's weight by a caller-given multiplier (biasing without guaranteeing); `reroll` draws twice and keeps the second. `forceOutcome` picks an exact index.
11. **`ActiveStatus` gains a generic `param?: string`**, resolving OQ-29's Ability Lock/Energy Lock blocker: Ability Lock's `param` is the specific locked ability id (checked in `actions.ts`'s `validateAction`); Energy Lock's is the locked `EnergyFamily` name (also `validateAction`, blocking any ability whose *effective* cost needs that family). Energy Cost Increase needed no such parameter — it just adds its magnitude onto NEUTRAL cost (`getEffectiveCost`, `actions.ts`), the one component any family can pay. All three move from OQ-29's deferred list to implemented; Resurrection Lock (checked in the `resurrect` effect) does too, since building resurrection this phase made it nearly free.
12. **`hasTag` and `secretScript` conditions still always return `false`** (`conditions.ts`): tags live on `CharacterDefinition`, which no engine runtime references yet (no roster exists before Phase 04); no secret script is registered in this file's own registry below. Both are honestly false rather than silently wrong — logged as OQ-31 alongside the other conditions-system gaps.
**Consequences:** Every one of phase-03-advanced-systems.md's eleven acceptance-criteria items has a passing, purpose-built test (`triggers.test.ts`, `snapshot.test.ts`, `rng-modifiers.test.ts`, plus additions to `damage.test.ts`, `effects.test.ts`, and `resolver.test.ts`) — 179 tests total, up from 124. `onMatchStart` is defined in the schema but never fired by `createBattle` (no passives exist to react to it before a roster does); `onTurnStart`/`onTurnEnd` fire once per living character at the very start/end of `resolveTurn`, which is a reasonable interpretation but not the only possible one. Both logged as OQ-31.

## ADR-011 — First five prototypes: small engine extensions three real character kits forced (Phase 04) — Accepted (2026-09-18)
**Context:** phase-04-first-five.md's five characters (Tortuga Rex, Mister Whiskers, Patient Zero,
Moonshot Maddox, Malachar) are the first real content built on top of Phases 01–03's engine. Several
of spec/03's named mechanics turned out to need small, generically reusable engine changes to express
at all — not because the spec's ambiguous, but because no prior phase's acceptance criteria exercised
these specific shapes. Each is the "simplest option that keeps the system reusable," per CLAUDE.md's
session protocol.
**Decision, by subsystem:**
1. **`Trigger.effectTarget: "subject" | "self"`, default `"subject"`** (`packages/content/src/schemas/
   condition.ts`; consumed by `packages/engine/src/triggers.ts`'s `evaluateEvent`). Every reactive
   effect previously landed on `gameEvent.subjectId` — whoever the event was *about* — never on the
   trigger's own holder. That's fine for "when I take damage, do X to myself" (holder == subject), but
   makes Malachar's passive ("whenever ANYONE dies, *I* gain a Soul") structurally impossible whenever
   `relation` isn't `"self"`. `effectTarget: "self"` redirects the effect's `targetIds` to the holder
   instead. This is exactly OQ-31(a)'s predicted next step ("revisit once retaliation-style Legends are
   designed") arriving on schedule. Default preserves every one of Phase 03's 179 tests unchanged.
2. **Consecration also blocks resurrection at the engine level** (`packages/engine/src/effects.ts`'s
   `resurrect` case): `hasStatus(target, SOUL_CONSECRATION.id)` now blocks a revive exactly like
   `RESURRECTION_LOCK` already did. This is spec/03's fourth Consecration rule ("cannot ... be
   resurrected"), implemented once, generically, for any future resurrection-capable character — not
   specific to Malachar or Father Bell (neither of whom casts `resurrect` this phase).
3. **`retargetQueuedAction`'s `queuedCharacterId`/`newTargetIds` are now optional**, defaulting to
   `ctx.targetIds[0]` and `[ctx.sourceId]` respectively (`packages/content/src/schemas/effect.ts`,
   `packages/engine/src/effects.ts`). Static ability content can't hardcode a real match's actual
   enemy ids, so a real Cheater ability (Mister Whiskers' Paw Swap) couldn't use this effect kind at
   all under Phase 03's schema, which required both fields as literal, pre-authored ids. The default
   reads as "redirect whichever enemy this ability targeted, onto me."
4. **An effect's own optional `target` field is now honored when it's `{ side: "self", ... }`**, for
   the `heal` and `modifyResource` effect kinds only (`packages/engine/src/effects.ts`,
   `resolveEffectTargets`). Every effect in one ability previously shared the ability's own resolved
   `targetIds` unconditionally, which made a cross-target ability — Malachar's Borrowed Life ("deal 20
   damage **to an enemy**, restore 20 HP **to himself**") — inexpressible. Full per-effect targeting
   (ally/random/lowestHp/...) would need threading a `BattleState` and `RngState` into `EffectContext`
   to re-run real targeting logic, a much larger change than any current content needs; `"self"` is
   trivially resolvable from `ctx.sourceId` alone, so that's the only side this phase implements.
   Logged as OQ-36 for the rest.
5. **Infection is now a real, ticking status** (`packages/content/src/data/statuses.ts`): just
   `tickBehavior: "damageOverTime"`, no new engine code, since DoT ticking already reads that field
   generically off any status (the same mechanism Bleed/Burn/Poison already used). Resolves OQ-29's
   Infection blocker now that Patient Zero is a real character needing it.
6. **`defaultResourcesFor(character): Record<string, number>`** (`packages/content/src/schemas/
   character.ts`) — the first characters with resources are also the first thing needing to turn
   `CharacterDefinition.resources`' `startingValue`s into the plain map `createBattle` actually takes
   (`CreateBattleCharacterInput.resources`). One small shared function instead of every future call
   site (a real UI, `packages/ai`'s bots, this phase's own scenario tests) re-deriving it by hand.
7. **`composePrompt`/`missingIdentityAnchors`** (`packages/content/src/schemas/art.ts`) — spec/04's own
   required deliverable ("Build a prompt-composer function that takes bible + shot type + global
   language and returns the prompt, then validate that authored prompts include the bible's identity
   anchors"). `CharacterArtSpec`/`CharacterVisualBible` were also restructured to match spec/04's
   documented schema shape (splash/portrait/battleAvatar/abilityIcon/transformation/
   secretSilhouette/legendReveal prompts; face/body/clothing/weapons/markings/species/age/silhouette/
   signature-props identity anchors) — the versions Phase 00 shipped were a simpler placeholder with
   no prior ADR recorded for the simplification, and nothing outside this phase's own new character
   data consumed the old shape, so there was nothing to preserve compatibility with.
8. **Malachar's "corpse" mechanics are approximations, not literal corpse-targeting** — see
   `docs/design/characters/malachar.md` for the full reasoning. In short: `TargetRule`-based targeting
   can never select a dead character (`targeting.ts` always filters to `alive`), and a Condition's
   `"enemy"`/`"ally"` refs only ever resolve to a *living* character (`conditions.ts`) — so nothing in
   the engine can express "target/query this specific corpse" yet. Corpse Command becomes a
   Souls-fueled bonus-damage strike; Raise the Forgotten summons a Thrall from nothing rather than a
   named body; You Belong to Me fields a slot-occupying `Summon` (a real "temporary fourth fighter,"
   per spec/03's coverage list) instead of resurrecting a specific enemy onto Malachar's team. All

## ADR-012 — Playable local 3v3: PWA foundation, the simple bot, and match-screen UI decisions (Phase 05) — Accepted (2026-09-18)
**Context:** phase-05-local-playable.md is the first real UI: a match screen driven entirely by the
engine, hotseat and vs-bot modes, a team picker, and a PWA foundation (manifest + offline-capable
service worker). Several implementation choices needed a decision the phase brief left open.
**Decision, by subsystem:**
1. **The service worker is hand-written, not generated by a workbox-based tool** (`apps/web/
   sw-template.js`, built by `veilbreakServiceWorkerPlugin` in `vite.config.ts`). A generated
   service worker is much harder to audit by hand for `scripts/verify-client-only.mjs`'s purposes —
   this game's whole asset list is small enough that a plain install/activate/fetch handler covers
   everything a generator would otherwise produce, and it stays something a human can read start to
   finish. The guard's `ALLOWLIST` now includes `sw.js`, since a service worker's own
   `fetch(event.request)` inside its fetch handler is what intercepting/serving same-origin requests
   *is*, not a call to a third party.
2. **Cache name includes a per-build id** (`CACHE_NAME = "veilbreak-__CACHE_VERSION__"`, substituted
   with `Date.now()` at build time): without it, `activate`'s cleanup (`caches.keys().then(...
   caches.delete)`) would never find anything to delete, since the same fixed name would just get
   reused/re-populated forever — verified live: rebuilding with a stale entry in the precache list
   left it there under a fixed name, but a version-suffixed name let the old cache actually get
   pruned on the next activate.
3. **Manifest and icon generation live in a separate pre-build script**
   (`apps/web/scripts/generate-manifest.ts`, run via `tsx` before both `dev` and `build` —
   package.json), not inside the Vite plugin that builds `sw.js`. Vite's own config-loading step
   bundles `vite.config.ts` with a minimal esbuild pass that treats workspace packages as external,
   so it cannot resolve `@veilbreak/content`'s own extensionless internal imports (ADR-003) the way
   `tsx` or the real app build can — confirmed by a real `ERR_MODULE_NOT_FOUND` when GAME_TITLE was
   imported directly in `vite.config.ts`. The service-worker-building plugin only needs the final
   build's own emitted file names (no GAME_TITLE), so it stays free of this problem; only the
   manifest/icon generator needs it, and runs as ordinary `tsx` tooling instead.
4. **Placeholder portraits are initials plus a hash-derived hue** (`apps/web/src/game/portrait.ts`),
   not literally each character's `CharacterArtSpec.colorPalette` (OQ-21's "regional color" phrase).
   A palette entry like `"weathered bronze"` is prose, not a valid CSS color value — deterministically
   hashing the character's own id into a hue is simpler than parsing/mapping every palette string to a
   real color, and satisfies the same goal (every character reads as a distinct, consistent color with
   zero external art).
5. **A character with no affordable or otherwise legal action must be explicitly "passed," not just
   left unqueued** (`MatchScreen`'s `skippedA`/`skippedB` state). `resolveTurn` is already fine with
   fewer actions than living characters (a missing action just means that character doesn't act), but
   the "Confirm turn" button's own enabling logic originally required every ready character to have a
   queued action — which made a turn permanently unconfirmable the moment any character couldn't
   afford anything (caught by manually playing a match in the browser pane, not by a test — logged as
   a lesson: the "component tests for validation feedback" acceptance criterion didn't happen to cover
   this path). A skip is UI-only bookkeeping; it never reaches `resolveTurn`.
6. **The simple bot (`packages/ai/src/simple-bot.ts`, `decideSimpleBotActions`) is deliberately not
   one of `BOT_LEVELS`** (BEGINNER/INTERMEDIATE/ADVANCED/EXPERT/LEGEND_BOSS, from the Phase 00
   scaffold). It exists only to satisfy this phase's own "random legal action, prefers kills" — for
   every living character on its team, it uses the real `validateAction` to enumerate legal
   (ability, target) pairs (never re-implementing targeting legality), prefers one whose flat
   top-level damage would drop the target's current HP to 0 or below, and otherwise picks uniformly
   at random. Phase 07 builds the real, tested BEGINNER-through-EXPERT ladder; logged as OQ-37 so
   that work doesn't confuse this stopgap for it.
7. **A visible turn timer, on by default and toggleable in Settings** (spec/05's own match-screen
   list names one; spec/06 OQ-08 already proposed the default "unlocked actions are dropped" and "the
   timer is optional in settings" for local play against bots). Expiry calls the exact same
   `confirmTurn` path a manual click would, locking in whatever's already queued and leaving every
   other ready character simply not acting that turn — no separate "what happens on timeout" logic to
   keep in sync with the normal confirm flow.
8. **`Trigger.effectTarget` was accepted as `"self"` only in Phase 04 (ADR-011); nothing about it
   changed here.** Every one of this phase's five characters played correctly in the browser pane
   exactly as scripted in their Phase 04 scenario tests (Nine Lives pre-charging Death Prevention,
   Infection ticking and building Outbreak Progress, etc.) — direct, live confirmation that Phase 04's
   engine work was correct, not just unit-tested in isolation.
**Consequences:** `pnpm run ci` is green; a full hotseat-vs-bot match was played end to end in the
browser pane (not just exercised by automated tests) confirming actions, statuses, resources, the
battle log, and bot decisions all render correctly from real engine state. The production build's
manifest, icons, and service worker were verified directly (fetched manifest, checked
`navigator.serviceWorker.getRegistrations()`, inspected the Cache Storage contents) via `vite preview`
rather than only assumed from source review. New open questions: OQ-37 (the simple bot's lethality
heuristic is a flat top-level check, not simulation-aware — fine for this phase, not a foundation for
Phase 07's real bot levels), OQ-38 (no React error boundary yet — a runtime exception anywhere crashes
the whole app with no recovery UI), OQ-39 (animation-speed and turn-timer settings are session-only;
Phase 09's persistence layer will need to own them for real).

**Addendum (CI):** jsdom 30 (added for component tests) crashes on Node 20's bundled undici (`webidl.util.markAsUncloneable is not a function`) — invisible locally (Node 24) and caught only by checking GitHub Actions. Both workflows now run Node 24, matching the local dev toolchain.

## ADR-018 — Local profile, saving, transfer, progression and replays (Phase 09) — Accepted (2026-09-19)
**Context:** phase-09-profile-progression.md and spec/06. **Decisions:** (1) **Saving.** Every save is one atomic IndexedDB transaction (`setMany`; a value that cannot be stored aborts the whole write) holding a checksummed envelope under `save` plus a rolling backup of the last 3 snapshots (`backup.1-3`). Backups rotate on milestones (a match, an unlock, an import or transfer) or when the previous snapshot is 30 s old, so quick settings changes do not churn them. Loading tries the current save, then each backup, then the Phase 08 `profile` key (so nobody loses progress), then a fresh profile, and never throws. The profile is **v2** with a real migration runner (`MIGRATIONS[n]` upgrades n to n+1, each tested); saves from a newer game are rejected, not guessed at. `navigator.storage.persist()` runs at startup and after install; Settings/Profile show Strong, Standard or Unknown. (2) **Install flow** (`platform/install.ts`, pure and tested): a friendly first-launch screen (native prompt on Chromium, Share to Add to Home Screen steps on iOS, a backup emphasis on Firefox desktop), always skippable; a gentle re-ask banner after the first Legend unlock, at most 3 asks, a day apart, never on Firefox desktop or once installed; the iOS move-progress path reuses the transfer code; a delete-the-app warning. (3) **Transfer.** Progress only (no history, replays or backups), encoded as a compact array payload with ids replaced by positions in a shared id table, deflated (fflate), wrapped as `VB1.` + base64url of [format byte][deflate][CRC32]. The table's fingerprint travels with the code, so a code from a different game version is refused rather than mis-decoded. Pair counts are clamped to 3, which is all the Codex reads, so transfer is lossy only there. A fully maxed profile built from real game content fits one QR (version 40, error correction L, 2,953-byte byte-mode limit) and was decoded back from a rendered image in tests. Codes and files are untrusted: size caps, a streaming inflater with a 400 KB output cap (compression bombs), checksums, and the zod schema as the real gate. The receiver shows the incoming and current summaries and confirms; the replaced save becomes a rolling backup. QR drawing (`qrcode`) and reading (`jsqr`) are bundled; the in-app camera scanner needs a secure context and falls back to paste. (4) **Backups.** One full JSON backup (profile plus replays, checksummed) via the Web Share sheet where files can be shared, else a download; restore through a file picker; optional File System Access auto-save, feature-detected and hidden elsewhere. (5) **Progression** is pure functions over the profile and a finished match (`game/progression.ts`, `game/finishMatch.ts`): account level (100, 200, 300... xp per level), missions and per-origin faction chains, eight secret achievements shown as cryptic hints until earned, and Legend trials. A Legend is an accomplishment: meeting one reveals it, winning its trial (your team against the Legend and two allies, played by the LEGEND_BOSS bot) unlocks it for team building. The Nameless One's boss encounter stays sealed until all eleven other Legends are unlocked and he is unlocked only after beating it. A bot's win never counts for the profile. (6) **Replays.** A replay is the setup, seed, energy rules and each turn's actions; the viewer re-runs the real engine (`runReplay`), reports an illegal turn instead of hiding it, and warns on a balance-version mismatch. The last 20 are stored, files and `#replay=` links (short matches) are supported. (7) The third-party libraries now live in one audited `vendor` chunk (React, qrcode, jsqr, fflate): qrcode's SVG writer contains the W3C xmlns identifier that the client-only guard would otherwise flag.
**Bugs fixed on the way:** the engine returned `matchEndedByTurnLimit` only in the log, not in the turn's events, so the match screen never ended a match at the turn limit (regression test added); `setMany` did not abort when a later value could not be stored.
**Consequences:** about 125 new tests (migrations, atomic saves and backup recovery, export/import round trip, transfer round trip through a rendered QR image, QR size budget with real content, hostile and oversized inputs, unlock evaluation from event logs, the Nameless One gate, install planning, replay determinism including a rewind, keyboard-operable install/profile flows, reload and transfer between two stores).

## ADR-019 — Serverless friend matches: the match protocol (Phase 10) — Accepted (2026-09-19)
**Context:** phase-10-friend-matches.md and spec/06 "Friend match by code". **Decisions:** (1) A new pure package, `packages/protocol`, holds the whole protocol; the web app only adds screens and saving. (2) **Messages** are `setup`, `commit`, `reveal` (seed or turn), `stateHash` and `resign`, each validated by a zod schema with length limits. They travel in **bundles**: everything the sender has not yet had acknowledged, plus how many of the friend's messages they have processed and their latest state hash. A bundle is compressed, checksummed base64url (`VM1.`), and also works as a `#match=` link fragment. Because a bundle re-sends anything unacknowledged, a lost or repeated code is harmless and each player needs only about one code per turn. (3) **Seed:** the host sends a SHA-256 commitment to a secret contribution; the guest replies with its own contribution chosen blind; the host reveals; the seed is a hash of both (the engine's RNG state is 32 bits, so the seed is too). The host cannot change its contribution after committing (a mismatching reveal is a fatal `wrongReveal`) and the guest chose without knowing it. Aborting instead of revealing remains possible for the host, and is unavoidable without a server. (4) **Each turn:** commit (a hash of the actions plus a secret salt); reveal only once both commitments are in, so nobody can adapt to a revealed move; the second committer may reveal in the same code; both sides verify the reveal against the commitment, validate the actions with the real engine (a smuggled illegal action is fatal `illegalAction`), then resolve locally. (5) **Per-turn salt mixing:** both salts are hashed together and folded into the RNG state before every turn, so rolls cannot be precomputed from the seed; the mixed RNG state is recorded per step, which lets a replay reproduce the match with no hashing. (6) **Verification:** SHA-256 over the canonical (sorted-key) JSON of the full state after every turn; each bundle carries the latest hash and any mismatch is a fatal `desync`. A handshake compares the balance version and a hash of every rule table the engine reads (`contentHash`), so a client with different rules cannot join. (7) Sessions are plain JSON, saved to IndexedDB after every step, so a match survives closing the tab (asynchronous play). Finished matches feed the same profile pipeline as local ones (xp, missions, history, a replay). (8) **Unlock rule** is a host option: "own unlocks" is labelled honor-based in the UI, "everything unlocked" lifts the restriction for both. (9) Non-fatal problems (garbled code, wrong match, own code, a gap) leave the session untouched; fatal ones (wrong reveal, illegal action, desync, handshake, invalid team) stop the match and say why in plain words. **Stretch (live WebRTC with manual signaling): not attempted.** The protocol is transport-agnostic (a code is just a string), so a data channel could carry the same bundles later; recorded here as the required outcome. No external request is made, and no STUN is used.
**Bugs found and fixed on the way:** the engine did not check that an action's ability belongs to the acting character's kit, so a friend could have used any character's ability (`abilityNotKnown`, regression test, test fixtures now declare kits); the turn's actions are paid for in fighter order (so both clients agree), and the planner now checks affordability in that same order.
**Consequences:** 32 protocol tests (two simulated clients finishing a full match by exchanging only codes and reaching identical state hashes; a wrong reveal, wrong salt, early reveal, changed seed and smuggled action rejected; seed non-bias; salt mixing; tampered state and stale hash detected; handshake mismatch; malformed, truncated, oversized, foreign and hostile codes) plus friend UI tests across three simulated page loads.

## ADR-020 — Local ranked ladder (Phase 11) — Accepted (2026-09-19)
**Context:** phase-11-local-ranked.md, spec/06 "Local ranked", OQ-05, OQ-09. **Decisions:** (1) **Rating:** integer Elo (K 40 during placements, 24 after). It is hidden: players see a division, placement progress and a coarse standing ("close to a promotion", "holding steady", "one bad streak from a demotion"), never the number. A draw is scored 0.5, which pulls both sides toward parity (OQ-09); a win always gains at least 1 and a loss always costs at least 1. Glicko-2 was rejected: with one player against bots there is no rating-deviation signal worth its complexity, and Elo is easy to explain and test. (2) **Divisions:** Bronze, Silver, Gold, Platinum and Diamond, each III to I, 100 rating apiece, plus the apex "Veilbreaker" at 1500; a new profile starts at 400 (Silver II). **Promotion** is immediate on reaching the next floor; **demotion** needs a fall 20 points below the current floor (buffer), so edge results do not flip the division. (3) **Placements:** the first 5 matches of every season; no division is shown until they finish; the division is then set from the rating but capped at Gold I. Bots during placements scale from the rating. (4) **Seasons:** calendar months in UTC (`YYYY-MM`), rolled lazily whenever the ladder is opened or a match is applied (idempotent). A rollover archives the finished season (the last 12 are kept), keeps half the distance from the starting rating, and starts placements again; records, streaks and season counters reset, while personal bests, usage and recent matches stay. Tying seasons to the balance version was rejected: balance versions are not calendar events and a player would not know when a season ends. (5) **Opponents:** skill by division (Bronze Beginner, Silver Intermediate, Gold and Platinum Advanced, Diamond and above Expert; Legend Boss is reserved for trials). The bot's rating is the player's plus a seeded nudge of up to 60. **Team quality** rises with the division: low divisions pick close to at random, higher ones weight picks by measured win rate, and from Platinum a bot often plays one of the twelve strongest known trios. The measurements come from `pnpm meta` (20,000 random-team INTERMEDIATE matches, seed 11, committed as `packages/ai/src/meta-pool.json`); rerun it when the balance changes. (6) **Legend policy (OQ-05, now settled):** bots below Platinum bring at most 1 Legend, Platinum and above at most 2; the player may bring any Legend they have unlocked, and the "Reveal every character" spoiler switch does not unlock Legends in ranked. (7) **Pick/ban (Diamond and above):** each side picks four and bans one of the other's four, and the remaining three play. The bot bans by skill: an Expert always takes the player's strongest pick by win rate, weaker bots sometimes ban at random. All choices are seeded by the match seed. (8) **Leaving a match unfinished counts as a loss.** The match is saved as `ranked.pending` the moment it starts; the next time the ladder opens (after a reload, closing the tab or navigating away) it is settled as a loss, so the tab cannot be used to dodge one. (9) All ladder state is the profile's `ranked` block (**profile v3**, migration 2 to 3, defaults). It is in the JSON backup and (standing, season record and personal bests) in transfer codes; usage, recent matches and past seasons travel with backups only, like history. Transfer codes made by the previous version (v2) still decode. (10) Ranked matches record a normal history entry and a replay (`mode: "ranked"`). **Bug found and fixed on the way:** the team picker only capped the picked number at the constant team size, so a four-fighter draft was impossible (regression-tested by the Diamond flow test); the history list also mislabelled Friend matches as "Hotseat".
**Consequences:** 82 new tests (rating curve and clamps; placement flow and the Gold I ceiling; promotion, buffer and demotion; streaks, bests and usage; season id, rollover, idempotence, skipped months, archive limit; forfeit; migration, backup and transfer round trips; simulated players of three strengths finding their level and not flip-flopping; bot skill, quality and Legend cap; pick/ban; meta-pool building; the ranked flow in the UI). The ladder inherits the balance concerns of OQ-48: because bots at high divisions favour measured win rates, they lean on Patient Zero and the Black Knight.

## ADR-021 — Balance drafts, developer mode and personal stats (Phase 12) — Accepted (2026-09-19)
**Context:** phase-12-dev-balance-tools.md, spec/06 "Balance tools" and "Analytics", spec/07 "Balance simulation". **Decisions:** (1) **A balance change is a `BalanceDraft`**: a small JSON file (`format: "veilbreak-balance"`, id, base version, notes, and a list of `{path, value}` edits). Paths address numbers by `library/id/json/path` (for example `characters/hydra/baseHp`). The set of editable numbers is found by walking the libraries (`listTunables` in `packages/content/src/balance.ts`): health, damage, healing, energy costs, cooldowns, durations, status and effect values, transformation requirements, random-outcome weights and the energy rules. Anything else is rejected. `applyBalanceDraft` clones the shipped libraries, applies every edit, re-validates each touched entry against its schema, and applies **nothing unless the whole draft is valid**; it returns the new libraries, a diff and warnings (damage or healing off the multiples-of-10 language). Integers only. (2) **Versions:** `SHIPPED_BALANCE_PATCHES` lists published drafts; `librariesForVersion(id)` gives the libraries for a recorded id (the base `phase-05-v1` or a published patch) or null. `runReplay` now resolves the numbers from the replay's own version, so an old replay keeps playing under its shipped numbers after a new version is published, and an unknown version is flagged instead of silently replayed. The empty list means no version has been published yet. (3) **Dev mode** lives entirely in `apps/web/src/dev` (workbench UI, IndexedDB drafts, simulation dashboard, Worker). It is loaded with a dynamic import guarded by the build-time literal `__DEV_TOOLS__` (true in dev and test builds, or a production build made with `VITE_DEV_MODE=1`); a dev build also needs `?dev=1` unless `VITE_DEV_MODE` forced it. In a normal production build the flag is `false`, the import is dead code and nothing dev-only is emitted. `scripts/verify-no-dev-mode.mjs` (in `pnpm ci`) scans the production build for the dev marker, the workbench text and the dev worker file, and **self-tests** by building with `VITE_DEV_MODE=1` into a temporary folder and requiring the markers to appear. The balance module itself (apply, versions) is in production because replays need it; only the editor and dashboard are not. (4) **Simulation:** `defaultSimDeps(libs)` and `playablePool(libs)` make the existing headless simulator run against any libraries; the workbench runs the shipped balance and the draft in a Worker (inline where there is no Worker), and `pnpm sim --balance file.json` does the same from a terminal. The dashboard shows character win rates side by side with outlier flags (the same 60%/40% bands as the report), first-player advantage, match length and the report's recommendations. **Recommendations are text only; nothing is ever applied automatically.** (5) **Player stats** (in the Profile screen): win rates by fighter, exact team and opponent from the last 50 matches, and favourite abilities and transformation counts from the newest stored replays (re-run through the engine, counting `abilityUsed` and `transformed` events for the player's side). History entries now record which side the device played (`humanSide`, optional, so no profile version change); hotseat is excluded because there is no single "you". All of it is computed on the device; there are no analytics SDKs and no aggregate data. (6) `docs/design/balance-workflow.md` describes the whole loop for a designer.
**Consequences:** the balance tools work without touching source, results are reproducible (draft plus seed plus bots), and publishing is one JSON paste plus a test. Known gap (OQ-65): the first published version also needs the new-match version id and UI text pointed at it.

(7) **Naming:** Chef Ramble's Devour constant is prefixed (Gashadokuro already exports `DEVOUR`). (8) The ranked meta pool was regenerated for 115 characters (60,000 matches). **Balance:** four tuning rounds against the 5,000-match simulation, mostly Chef Ramble (77% to 55%: the base recipe and the Fiend both weakened); outliers recorded in `docs/balance/phase13-region10-notes.md`.
**Consequences:** 115 playable characters. Region 10 tests: 22 scenario tests, 7 roster checks with Legend checks, coverage additions. Known: Johnny Feedback (44%) and The Mime (44%) low, DJ Cataclysm (59%) and Orpheon (58%) high (OQ-101).

## ADR-033 — Art audit and export (Phase 14) — Accepted (2026-09-20)
**Context:** phase-14-art-specs.md, spec/04. Every character already had a visual bible and art spec (Phase 13 required them per character), so this phase is an audit and a hand-off file rather than new art. No image is generated here: there is no image tool in the development environment, and the deliverable is prompts and validation for an external generator or an artist. **Decisions:** (1) **`auditArt`** (`packages/content/src/artAudit.ts`) checks every playable character and returns errors and warnings: empty fields, missing identity anchors, style imitation, franchise names, living-artist names and artist credits, requests for text or logos (after removing the standard "no text, no logo" negatives), a Secret with no silhouette, a Legend with no reveal, a transformed state with no art prompt, fewer than four icons, a spec no longer at `draft`; and warnings for a prompt without the global art language, identical prompts or palettes, and very long prompts. It runs as a test over the real roster, so it is part of `pnpm run ci`, and `pnpm art:audit` prints it. (2) **Fixes the audit forced:** 60 older specs had no `colorPalette`, so the schema now derives it from `paletteConcept` (a transform on `characterArtSpecSchema`); Malachar had no silhouette prompt; The Forgotten Titan and Chef Ramble had no transformation art (`buildArt` now takes `transformationScenes`); and three wordings that could be read as a request were changed (Rusalka's "drawn like a veil", The Lawyer's "small print", Moonshot Maddox's "no real-world logos"). (3) **`buildArtExport`** and `pnpm art:export` write `docs/art/art-specs.json`: every character with its bible, palette, region, review priority and every asset (portrait, splash, battle avatar, icons, transformation, silhouette, reveal) with a stable id, the shared negative prompt and a canvas size, plus `pipelineGuidance` and `culturalGroups` ordered by review priority. It is deterministic (no dates), a test fails if the committed file is stale, and the export refuses to run while the audit has errors. (4) **Consistency approach:** the look comes from one shared framing and global art language in every prompt, per-character identity anchors and per-region palette vocabulary; the guidance tells the pipeline to make a four-character reference set first, freeze settings, generate the portrait first and reuse it as a reference, and never add styles or artists. The audit can check the prompts; it cannot check that finished images match. (5) Every spec stays `draft` with `culturalConsultationNeeded` set (OQ-12). **Consequences:** 873 assets for 120 characters, and `docs/art/README.md` explains the workflow. Known: the region strings are free text in about 20 variants, so cultural groups are matched by keyword (OQ-104).

## ADR-034 — Phase 15: balance pass, accessibility, performance, security and offline audits — Accepted (2026-09-20)
**Context:** phase-15-balance-polish.md. Everything below is measured; the full report is `docs/balance/phase15-report.md`. **Decisions:** (1) **Simulation:** 30,000-match baselines at INTERMEDIATE and ADVANCED (EXPERT is about 20 times slower; a 30,000-match run was abandoned, so EXPERT was not used for the pass), all detectors from Phase 07 read, and every finding acted on or logged. (2) **A resource lock was real:** 10% of matches had a team with no legal action for three turns, almost always a last survivor on a 2-per-character energy trickle unable to pay a specific mix of families. The energy rules gained `generation.minPerTeam` (a floor on a team's units per turn; default 0, set to 4 in the shipped rules): a last survivor now gets 4 units instead of 2. Result on 5,000 INTERMEDIATE matches: lockouts 594 to 189, matches reaching the turn limit 118 to 43, resurrection loops 6 to 0. Raising `perLivingCharacter` instead (3, 4) was tried and made the spread of win rates worse, so it was rejected. (3) **A balance patch, `phase-15-v1` (`docs/balance/drafts/phase-15-v1.json`, 58 edits):** cheaper heavy abilities and more health for the weakest older kits (Behemoth, The Referee, Koschei, Maestro Nocturne, The Marionettist, Oni of the Red Gate, Zeiron, Malachar, Moonshot Maddox, Puca, The Siren, and others), and small trims for the strongest new ones (The Firebird, Draugr, Patient Zero, El Magnífico, King Croak, The Lawyer, Rusalka, Anubian Judge). It was simulated with `pnpm sim --balance` first, in two rounds, then **baked into the character source** by `scripts/bake-p15.py`, and verified value by value (4,091 tunables compared before and after: the only differences are the 58 edits). The standard deviation of character win rates fell from 9.4 to 7.9 points, characters under 35% from 10 to 1, over 65% from 3 to 1. Because no build has shipped to players yet, the base version id stays `phase-05-v1`; from the first public release every balance change must go through `SHIPPED_BALANCE_PATCHES` (docs/design/balance-workflow.md), and OQ-65 (new matches recording the newest id) must be closed first. Design notes for the 24 changed characters carry a Phase 15 section listing the new values. (4) **Accessibility:** axe-core now audits every main screen in CI (no violations), a stylesheet audit checks WCAG AA colour contrast for both themes (one real failure, the enemy colour on a raised surface at 4.43:1, was fixed by brightening it), and tests check reduced motion, relative text sizes and visible focus. (5) **Performance:** a whole simulated turn (both bots planning and the engine resolving) costs about 0.2 ms at INTERMEDIATE, 0.5 ms at ADVANCED and 4 ms at EXPERT on the development machine, against a 10 ms target; a CI budget test enforces it. `scripts/verify-bundle-budget.mjs` (in `pnpm ci`) fails if the initial download exceeds 340 KB gzip (now 279 KB) or the bot worker exceeds 190 KB (now 125 KB). Region-by-region lazy loading of content was not done: every region's data is needed by the character browser, and no art ships yet. (6) **Security:** fuzz tests (deterministic mutations, hostile literals, prototype-pollution keys, oversize input) show that backup import, transfer codes, replay files and friend-match codes never throw and reject damaged input; CSP tests check no eval, no inline script, no remote host, and now `worker-src`, `manifest-src` and `frame-src` are pinned; source scans confirm no `eval`, no network call in game code and a single innerHTML sink (the QR picture), whose markup is tested to contain only drawing elements. (7) **Offline/PWA:** a real-browser test in Chromium (the built-in browser: fresh visit, then the server stopped, then a `?dev=1` navigation) loaded the whole app from the service worker, and it found two real bugs, both fixed: `caches.match` searched every build's cache (a stale index.html could meet new scripts), and a host that sends `Vary: Origin` made every precached module script miss. The worker also no longer takes over instantly (it waits for old tabs, or a SKIP_WAITING message), only answers same-origin GETs, opens navigations with a query string, and falls back to the cached shell. Ten unit tests cover it. The manifest gained `id`, `lang`, `categories`. **Not done:** Firefox and WebKit runs, a real iPhone and Android device, Lighthouse, Playwright, and the single-file build (OQ-106 to OQ-108). **Consequences:** 1,082 tests, one energy-rule field, one balance patch, three new audits in CI.

## ADR-037 — Pinned back/start bar and two ways to start over — Accepted (2026-09-20)
**Context:** Playtest feedback: on the team screens Back and Start match sat below a 119-fighter roster, so leaving or starting meant scrolling to the bottom. Testers also wanted to restart the build-up of the game, either keeping their unlocked fighters or from nothing. **Decisions:** (1) `ScreenBar` pins Back, a short status ("2 of 3 picked") and the primary action under the main navigation on the team setup, Legend trials, and friend host/join/menu screens. ## ADR-038 — Unlock quests replace "meet it in a match" — Accepted (2026-09-20)
**Context:** Playtest feedback. 93 of 119 fighters were open from the first launch, every Legend trial was open from level 1, Secrets unlocked by simply appearing in a bot's random team (about a third of matches), and missions and levels only gave XP. A tester also said "meet it in a match" removes the sense of a goal, and suggested per-fighter missions such as winning a number of matches with a character. **Decisions:** (1) Starter roster: every Core fighter plus the Moon Rabbit (24), so all main roles are covered. (2) Every other fighter (except the Nameless One) has a quest of one to three steps, generated from roster data in `apps/web/src/game/quests.ts` (win with a named starter, win with a role, win with two fighters of one origin, win quickly, win without losing a fighter, win against a Legend team, win with three different roles). Steps are ordinary missions, so progress, XP and the save file reuse existing machinery. Rare fighters open in seven tiers by kit complexity (levels 1, 2, 3, 4, 5, 7, 9); Secrets show their quest only after being met (from level 3); Legends need level 4 to 14, one level apart, plus a three-step quest, then the existing trial. Meeting a fighter now only reveals its Codex entry. (3) Bots leave Secrets out of your opponents below level 3 and Legends below level 4, so a new player is not matched against them. (4) `profile.unlocks.fighters` records finished quests; `profile.unlocks.model` is 2 for new profiles and 1 (the default) for older saves, which keep every Core, Rare and Secret fighter and every open trial. Legends stay won, never granted. (5) The transfer code now packs the mission and fighter lists as bitsets and leaves out counters of finished missions, so a full save still fits one QR code. (6) The friend match host rule now defaults to "Own unlocks only". **Consequences:** all tuning numbers are constants at the top of `quests.ts`. Tests check that every quest step can be completed by a team of starters, that gating works, and that older saves are unchanged. About 94 quests, 205 steps and 12,700 XP of quest rewards in total. Not yet playtested for pace; expect to retune tiers, goals and Legend levels.

## ADR-039 — First-run tutorial as a coached real match — Accepted (2026-09-20)
**Context:** Playtesters had no guidance: the first match dropped a new player onto the full board. **Decisions:** (1) The tutorial is an ordinary match (Tortuga Rex, Hydra and the Moon Rabbit against the Scarecrow, Red Oni and the Honey Badger, beginner bot, no turn timer) with a `TutorialCoach` tip pinned above it. `tutorialTip` in `apps/web/src/game/tutorial.ts` picks one of seven short tips from the turn, whether a target is being chosen, and how many fighters have an action; it only reads state, so the match plays exactly like any other. (2) A new profile has `tutorial.status = "new"` and is offered the tutorial on the Play screen ("Start the tutorial" or "I know how to play"). Saves without the field count as "done", so existing players are never nagged. Finishing the match sets "done", skipping sets "skipped"; both are stored and travel in the transfer code. "How to play" stays on the Play screen so it can be replayed. (3) "Reset progress" keeps the status; "Erase everything" makes the profile new again, so a developer can see the first-run experience. (4) A tutorial match counts as a normal bot match for XP and quests. **Consequences:** unit tests cover every tip and the setup, and flow tests cover offer, start and skip. It has not been tried with real first-time players yet.

## ADR-040 — Single-file build for opening from disk — Accepted (2026-09-20)
**Context:** OQ-107. The normal build needs a web server: module scripts, the service worker and the bot's Web Worker do not load from a `file:` URL. People who receive a zip want to double-click a file. **Decisions:** (1) `pnpm build:single` runs `vite build --mode single` and then `apps/web/scripts/inline-single-file.mjs`, giving `apps/web/dist-single/veilbreak.html`. In this mode Vite builds one chunk (no vendor split), inlines fonts and images as data URIs, and omits the service worker plugin. The bot worker is bundled with `?worker&inline` and started from a blob (`__SINGLE_FILE__` build flag in `useBotWorker.ts`; the branch is removed from the normal build). (2) The script and styles move into the page; the Content-Security-Policy is rewritten to `default-src 'none'`, the inline script pinned by its SHA-256 hash, `worker-src blob: data:`, `connect-src 'none'`. No service worker is registered, so there is no offline caching or install prompt: the file itself is the offline copy. Saves use IndexedDB scoped to `file://`, which some browsers isolate per file path, so back up before moving the file. (3) `scripts/verify-single-file.mjs` (part of `pnpm ci`) fails if the page references anything external, allows the network, or lets any inline script run. Dev mode is off in this build. **Consequences:** about 1.7 MB. Checked over http with only that file being served: the tutorial and a bot turn (the inlined worker) worked with no other request. Not yet tried from a real `file://` URL in each browser (part of OQ-106).

**Amendment (2026-09-20):** a real `file://` test in Chromium showed the inlined worker, built as an ES module, closed at once (a module worker made from a blob does not start on a `null` origin), so the bot never answered. The single-file build now bundles the worker as a classic script (`worker.format: "iife"`), and `verify-single-file` fails if a module worker comes back. Checked with Playwright: Chromium and WebKit load the file from disk, play a bot turn and keep the save across a reload. `scripts/manual/cross-browser-check.mjs` repeats that check by hand.
