# Architecture Decision Log

Format: `ADR-NNN — Title — Status (Proposed/Accepted/Superseded) — Date`, followed by Context / Decision / Consequences. Also register every custom character script here (see CLAUDE.md, rule 3).

## ADR-001 — Tech stack — Accepted (2026-09-17, Phase 00)
**Context:** The engine must be shared by the UI, bots, simulation, and friend-match verification. It must be deterministic, data-driven, and run entirely client-side (ADR-002).
**Decision:** pnpm TypeScript monorepo; pure `packages/engine` (integer math); `packages/content` with zod schemas; `packages/ai` (Web Workers + Node dev CLI); `packages/persistence` (IndexedDB); React + Vite static app; Vitest + Playwright.
**Consequences:** One engine codebase everywhere. The output is static files deployable to any static host. Confirmed unchanged during Phase 00 scaffolding; see ADR-003 for one addition (packages consumed as source, no per-package build step).

## ADR-003 — Workspace packages consumed as TypeScript source — Accepted (2026-09-17, Phase 00)
**Context:** `packages/engine`, `packages/content`, `packages/ai`, and `packages/persistence` are internal-only — nothing outside this monorepo ever imports them as published npm packages.
**Decision:** Each package's `package.json` points `main`/`types` at `src/index.ts` directly instead of a compiled `dist/`. `apps/web` (Vite) and Vitest consume that TypeScript source directly; each package's own `typecheck` script (`tsc --noEmit`) is the only place `tsc` runs on it. `apps/web` is the sole package with a real build step (`vite build`). Relative imports inside every package use extensionless specifiers (`./common`, not `./common.js`) — Vite/Vitest do not remap a `.js`-suffixed relative import back to its `.ts` source the way `tsc`'s `moduleResolution: bundler` would if the package were compiled to real `.js`, so extensionless imports are the form that resolves correctly everywhere (tsc, Vite, and Vitest) given this decision.
**Consequences:** Faster iteration (no build step between packages during Phases 00–08). No package here can be published standalone without adding a build step later — acceptable since none currently need to be.

## ADR-002 — Client-only platform — Accepted
**Context:** Owner requirement: no backend, no database, no server-side processing, no authentication requirement, and no external API dependency for core functionality.
**Decision:**
- Server authority is replaced by the local engine for solo play, and by commit-reveal plus deterministic replay verification for friend matches.
- The database is replaced by IndexedDB with versioned saves and export/import.
- Accounts are replaced by an automatic local profile.
- Online ranked is replaced by local ranked against bots.
- The admin panel is replaced by dev mode with exported balance files.
- Cross-player analytics are replaced by simulation reports plus personal stats.
**Consequences:** No global leaderboards, cross-device sync (except manual export), or tamper-proof unlocks. Friend matches are asynchronous by code; live P2P is optional. Hosting cost is effectively zero, and the game works offline.

## ADR-004 — Recursive zod schemas need a loosened Input type; the client-only guard exempts an audited vendor chunk — Accepted (2026-09-17, Phase 00 verification)
**Context:** Running the real Phase 00 acceptance criteria (`pnpm install && pnpm run ci`) after installing Node/pnpm surfaced two classes of bug the hand-review in the same session had missed.
**Decision:**
1. `effectSchema`, `randomOutcomeSchema`, and `randomOutcomeBranchSchema` (the mutually-recursive Effect/RandomOutcome types in `packages/content/src/schemas/effect.ts`) are annotated `z.ZodType<Output, z.ZodTypeDef, unknown>` instead of the single-argument `z.ZodType<Output>`. A single-argument annotation forces the schema's Input type to equal Output, but nested schemas with `.default()`-backed fields (e.g. `targetRuleSchema`) have an input shape strictly looser than their output shape, which real callers never notice because they always `.parse(value: unknown)`, never a value pre-typed as `Effect`. `exactOptionalPropertyTypes` was also dropped from `tsconfig.base.json` for the same family of reason (it does not compose with zod v3's `.optional()`/`.default()` output typing).
2. `apps/web/vite.config.ts` isolates React into its own `vendor` chunk (`build.rollupOptions.output.manualChunks`), and `scripts/verify-client-only.mjs` excludes that chunk from its external-URL/networking-API scan entirely (`VENDOR_CHUNK_PATTERN`). React's bundled internals contain strings that look like violations under naive scanning — W3C XML/SVG/MathML namespace URIs (DOM API identifiers, never fetched) and an inert `reactjs.org/docs/error-decoder.html` link embedded in minified error text — that have nothing to do with the app's own behavior. `apps/web/vite.config.ts` also sets `build.modulePreload: false`: Vite's default modulepreload polyfill contains a real (same-origin, harmless) `fetch(` call the guard can't statically distinguish from a call to a third party, and this single-entry Phase 00 app doesn't need the prefetch optimization it exists for.
**Consequences:** The client-only guard now enforces its rule against code this project actually writes, and treats a vendor dependency's internals as something to audit once by hand when added to `manualChunks.vendor`, not something to pattern-match on every CI run. Adding a new production dependency to the vendor chunk should get a one-time manual check that it doesn't call real network APIs.

## ADR-005 — EnergyPool is an explicit object schema, not an enum-keyed z.record — Accepted (2026-09-17, Phase 01)
**Context:** `packages/engine/src/energy.ts` needs a fully-required `{ MIGHT, FOCUS, SPIRIT, CHAOS }` type to read and write pool amounts without `?? 0` guards everywhere. `BattleState.energyPools` originally typed each player's pool as `z.record(energyFamilySchema, z.number())`.
**Decision:** zod v3 infers an enum-keyed `z.record`'s output as `Partial<Record<Family, number>>` (every key optional) rather than a fully-required record — real `tsc` output confirmed this the moment `packages/engine` tried to use it as a fully-required type. Added `energyPoolSchema` (a plain `z.object` with all four families required) to `packages/content/src/schemas/common.ts`, exported as `EnergyPool`, and used it for `BattleState.energyPools`'s value type (the outer map is still `z.record(idSchema, energyPoolSchema)`, keyed by playerId, which stays a proper `Record<string, EnergyPool>` since string-keyed records aren't downgraded to `Partial`).
**Consequences:** One canonical `EnergyPool` type, owned by content, used by the engine without defensive `?? 0` reads. General lesson for later phases: prefer `z.object` over `z.record(z.enum(...), ...)` whenever every enum member is genuinely always present.

## ADR-006 — Energy generation semantics: "fixed" mode and createBattle's turn-1 pass — Accepted (2026-09-17, Phase 01)
**Context:** spec/06's `EnergyRules.generation.mode` names `"random"` and `"fixed"` but only fully specifies `"random"` (OQ-03's default). Separately, the resolution order (spec/01) places "Resource generation" second-to-last (tier 14) and "Next turn" last (tier 15) — meaning a turn's generation really produces the *next* turn's energy, and turn 1 has no previous turn to have generated anything.
**Decision:** `"fixed"` mode grants every family `perLivingCharacter * livingCharacterCount` units directly, with no RNG draw — the simplest reading that still scales with team size the same way `"random"` mode's *total* unit count does, just without randomizing which family each unit lands in. `createBattle` (packages/engine/src/resolver.ts) runs one `generateEnergy` pass per team before returning the initial state, using the same `EnergyRules` the match will use, so OQ-03's "no energy on turn 1 for the initiative player" is meaningful (the non-initiative player actually has turn-1 energy) instead of vacuous (neither player would have any).
**Consequences:** `CreateBattleConfig` now requires `energyRules`, not just `matchFormat`. A caller must supply the *same* `EnergyRules` to `createBattle` and every subsequent `resolveTurn` call, or turn-1 energy and later turns' energy will be generated under inconsistent rules.

## ADR-007 — Resolver scope and cooldown timing (Phase 01) — Accepted (2026-09-17, Phase 01)
**Context:** phase-01-battle-core.md scopes the resolver to RNG, energy, action validation, and tier-ordered resolution — explicitly not the full combat/status/transformation systems (Phases 02–03).
**Decision:**
1. `packages/engine/src/effects.ts` (`applyEffect`) implements only `damage`, `heal`, `sequence`, and `randomOutcome` — enough to prove determinism and tier ordering end-to-end. Every other `Effect` kind throws a explicit "not implemented until a later phase" error rather than silently no-op'ing, so a future character definition can't accidentally depend on a mechanic (statuses, transformations, summons, resource/energy-modifying effects) that doesn't exist yet.
2. `Ability` gained an optional `resolutionTierId` field (`packages/content/src/schemas/ability.ts`); unset, the resolver defaults it to `STANDARD_RESOLUTION_TIER_ID` ("standard-attacks-support"). This is what makes "reordering the resolution-order config reorders events" (the phase's own acceptance criterion) meaningful to test at all.
3. Cooldown reduction (tier 13) explicitly skips any `characterId:abilityId` pair used during the *same* turn's action-resolution tiers. Reducing a freshly-set cooldown in the same pass would make `cooldown: N` only ever block `N-1` turns, since tier 13 runs later in the same turn as tier 6 where the ability was used and its cooldown was set.
4. The `death-checks` tier (10) marks `alive: false` and emits a `death` event, but does not determine a match winner from a team wipe (OQ-09's draw rule) — that belongs to Phase 02's "Death, resurrection, and death-adjacent rules". The only win-condition Phase 01 implements is OQ-14's max-turn HP-percentage tiebreak, since it was explicitly listed as a Phase 01 deliverable.
5. Only `turnModel: "simultaneous"` actually resolves (`resolveTurn(state, actionsA, actionsB, deps)` takes both players' actions together). `"alternating"` exists as a schema value (OQ-01) but has no resolver implementation yet — logged as a new open question rather than built speculatively ahead of any content that needs it.
**Consequences:** Phase 01's engine is real and tested, but a character/ability with a non-attack effect (a status, a transformation trigger, a summon) will throw at resolve time until Phase 02/03 extends `applyEffect`. That's intentional — it surfaces missing engine support immediately instead of a mechanic quietly doing nothing.

## ADR-008 — CI workflows let `packageManager` in package.json set the pnpm version — Accepted (2026-09-18)
**Context:** GitHub Actions CI had been failing since the very first Phase 00 push (both `ci.yml` and the new `deploy.yml`), silently — `pnpm run ci` was only ever verified locally, and no one checked Actions until setting up Pages surfaced it.
**Decision:** `pnpm/action-setup@v4` now refuses to run when both its own `version` input and `package.json`'s `packageManager: "pnpm@9.12.0"` field are set ("Multiple versions of pnpm specified"). Removed the `version: 9` input from both workflows; the action now reads the version from `packageManager` alone, which was already the source of truth locally.
**Consequences:** Local `pnpm run ci` passing is not sufficient evidence that GitHub Actions CI passes — check `gh run list` (or the Actions tab) after every push until this project has a habit of doing so automatically. This was two full phases (00 and 01) landing on `main` with red CI; nothing caught it because nothing looked.

## ADR-009 — Combat primitives: the status/damage/targeting model (Phase 02) — Accepted (2026-09-18)
**Context:** phase-02-combat-primitives.md needs a real status engine, a documented damage pipeline, and TargetRule evaluation (taunt, untargetable, random/lowest/highest-HP), landing on top of Phase 01's resolver.
**Decision, by subsystem:**
1. **ActiveStatus model** (`packages/content/src/schemas/battle.ts`): one record per `{characterId, statusId}`, with `stacks` (application count, capped at the definition's `maxStacks`) and `magnitude` (the most recent application's strength). Effective strength for any math is always `magnitude * stacks` — one rule, applied uniformly to Shield's absorption pool, Damage Reduction's flat reduction, a DoT/HoT's per-tick amount, and Damage Amplification/Weakness's modifier. A status without a numeric magnitude (Stun, Taunt, ...) just never has anyone read it.
2. **Stacking semantics** (`packages/engine/src/statuses.ts`, `applyStatusToCharacter`): `"none"` ignores a reapplication while active; `"refresh"` replaces duration and magnitude, keeps the stack count; `"stack"` adds a stack and replaces magnitude, duration untouched; `"stackAndRefresh"` does both. There is no per-stack independent expiry — all stacks of one status on one character share a single duration timer. Shield's absorption specifically collapses to a single stack at the reduced magnitude once damage consumes part of it (`setStatusMagnitude`), rather than trying to decrement across multiple stacked shield instances.
3. **Damage type table** (`packages/content/src/schemas/effect.ts` `DamageType` doc comment): normal runs the full pipeline; piercing skips only damage reduction and shield; affliction additionally skips invulnerable and reflect/counter, but amplification/weakness still applies to it (innate vulnerability, not defense). DoT ticks (Bleed/Burn/Poison) resolve as `"affliction"` — they're meant to punish reliably regardless of the target's defenses.
4. **Damage pipeline order** (`packages/engine/src/damage.ts`, `resolveDamage`): invulnerable → reflect/counter → amplification/weakness → damage reduction → shield → HP, exactly as phase-02-combat-primitives.md names it. Reflect fully redirects (target takes nothing, source takes the raw pre-mitigation amount, itself unmitigated to avoid reflect-loop recursion); Counter adds its own flat damage back at the attacker in addition to — not instead of — the target's own damage.
5. **Status duration exemption extended from ADR-006** (`decrementStatusDurations`'s `exemptStatusIds`): a status applied (or refreshed) in one tier of a turn is not decremented by that same turn's post-turn-effects tier, for the same reason a freshly-set cooldown isn't reduced by that turn's cooldown-reduction tier. Net effect: `durationTurns: N` means the status is active (and ticking, if it's a DoT/HoT) for the turn it's applied plus N further turns — N+1 total — mirroring how `cooldown: N` blocks exactly N turns after the one it's set on.
6. **Taunt redirects rather than rejects** (`packages/engine/src/targeting.ts`): when Taunt narrows the enemy-side candidate pool, an explicit `scope: "single"` selection outside that pool is silently redirected to the taunter(s), not treated as an illegal-target error. Treating it as an error would make a taunting tank's team immune to single-target attacks entirely, which defeats the entire point of Taunt.
7. **Cooldown Increase/Reduction** (resolver.ts's cooldown-reduction tier): net decrement per turn = `max(0, 1 + reductionMagnitude - increaseMagnitude)`, still exempting cooldowns just set this same turn.
8. **Deferred statuses**: beyond spec/06's own three (Infection, Soul Consecration, Death Prevention), nine more ship as fully valid, applicable, stackable, dispellable StatusDefinitions with no unique engine hook yet: Curse, Fear, Petrification, Mark, Stealth, Exposed, Resurrection Lock (spec never defines a concrete mechanic for these), and Energy Lock, Energy Cost Increase, Ability Lock (each needs a per-application parameter — which family, which ability — that the single-`magnitude` ActiveStatus model can't express without a real character forcing the design). Logged as OQ-29.
9. **`drainEnergy`'s grant-to-self is uncapped**: `applyEffect` has no `EnergyRules` in scope to check the pool cap against. Logged as OQ-30 rather than threading `EnergyRules` through the whole effect pipeline for one edge case with no character exercising it yet.
**Consequences:** The 19 statuses phase-02-combat-primitives.md's acceptance criteria actually exercise (Stun, Silence, Invulnerable, Untargetable, Damage Reduction, Shield, Counter, Reflect, Bleed, Burn, Poison, Anti-Heal, Healing Reduction, Healing Amplification, Cooldown Increase, Cooldown Reduction, Taunt, Damage Amplification, Weakness) are real and tested end to end. The remaining 13 are honest placeholders, not silent no-ops — nothing pretends they do something they don't.

## ADR-010 — Advanced systems: triggers, transformations, summons, death extensions, RNG manipulation, Cheater hooks (Phase 03) — Accepted (2026-09-18)
**Context:** phase-03-advanced-systems.md is the largest single phase so far: an event-driven trigger/passive engine, the transformation and summon systems, death prevention/erasure/resurrection, state snapshots, and every remaining spec/01 RNG-manipulation and Cheater mechanic. Every design choice below is the "simplest option that keeps the system reusable" for an ambiguity the spec left open, per CLAUDE.md's session protocol — none were destructive/irreversible, so none blocked on a question back to the project owner.
**Decision, by subsystem:**
1. **New `PassiveDefinition`** (`packages/content/src/schemas/passive.ts`): a standalone `{trigger, condition?, effects}` bundle, referenced by `CharacterRuntimeState.passiveId` (itself new — swappable by a Transformation's `changes.passiveId`). Spec/02 describes reactive hooks living on statuses (`StatusDefinition.triggerTiming`, already schema'd in Phase 00) but never names an equivalent for a character's own passive; without one, "Triggers and Conditions" would have nothing but statuses to attach to.
2. **One trigger evaluator for both passives and statuses** (`packages/engine/src/triggers.ts`, `evaluateEvent`): every living character is scanned each event for (a) its current passive and (b) each active status's `triggerTiming`, using the same `Trigger` (`event` + new `relation` field + optional `condition`) and the same `evaluateCondition` (`conditions.ts`, new). `relation: "self" | "ally" | "enemy" | "any"` is what makes "onDeath (any/ally/enemy)" concrete — computed from whether the trigger holder and the event's subject share a team.
3. **Trigger-fired effects always target the event's subject** (`targetIds: [gameEvent.subjectId]`), not a resolved `TargetRule` — a passive/status's effects aren't wrapped in an ability with its own targeting, and building a second targeting path for reactive effects was more machinery than any acceptance criterion needed. A caught test bug (a "thorns" fixture assuming it could hit "whoever attacked me") is the concrete evidence this would have silently done the wrong thing — logged as OQ-31 rather than building real reactive targeting speculatively.
4. **Recursion guard, `MAX_TRIGGER_DEPTH = 5`** (`triggers.ts`): a trigger's own effects can produce events that fire more triggers (a passive that deals damage is itself an onDamaged/onDamageDealt event); depth-capped rather than left to recurse, logging `recursionGuardTripped` and stopping. Verified with a genuinely self-perpetuating fixture (a "when damaged, take 1 more damage" passive) rather than a contrived two-character loop, since passive effects target the event subject (point 3) — a cross-character ping-pong needs real attacker-targeting this phase doesn't have.
5. **Erasure is a distinct event, not just fatal damage** (`effects.ts`'s `erase` kind, emitting `"erased"`): `deriveGameEvents` (triggers.ts) maps a `"death"` AppliedEvent to `onDeath`/`onKill`, but never maps `"erased"` to anything — that omission alone is the entire mechanism behind spec/02's "erasure that bypasses death triggers" (Shiro). `resolver.ts`'s death-checks tier only marks a character dead (and only then emits `"death"`) when it *finds* one at ≤0 HP with `alive` still `true`; `erase` already set `alive: false` directly, so that tier silently skips them.
6. **Kill attribution via a same-turn "last damager" map** (`resolver.ts`'s `lastDamageSourceByTarget`): `"death"` itself carries no attacker, so a transient per-turn `Map<targetId, sourceId>` (updated on every `"damageDealt"` event) supplies the death event's `sourceId`, which `deriveGameEvents` uses for `onKill`'s subject. Reset every turn — a kill only credits whoever landed the *most recent* hit this turn, not a full damage-contribution ledger.
7. **Death Prevention floors at 1 HP and self-consumes** (`damage.ts`'s `applyHp`): a save is single-use per application, matching OQ-06's "consumed even if the rewound turn kills again" pattern reused here for consistency, and floors rather than fully blocking (Aurelia "cannot fall below 1 HP", not "cannot be damaged").
8. **Summons: attached (non-slot) ones absorb, slot-occupying ones don't** (`summons.ts`, `damage.ts`): `Summon.occupiesSlot: false` (attached summons, spec/06's "absorption counters") makes `resolveDamage` redirect damage meant for the owner into the summon's own HP first, with overflow beyond its remaining HP continuing into the owner's own pipeline; `occupiesSlot: true` ("temporary fourth unit") summons don't intercept anything, since full independent targeting for a fourth unit is a larger feature no acceptance criterion needed yet (logged as OQ-32). `instanceId` is derived deterministically from `(owner, summonId, existing-count)`, not a module-level counter or a fresh RNG draw — CLAUDE.md rule 4 bans hidden mutation, and a counter living outside `BattleState` would make identical calls from different states collide or diverge.
9. **Transformation preserves statuses by never touching them, and rescales current HP by ratio** (`transformations.ts`): `changes.maxHp`, if present, scales current HP by `newMax/oldMax` rather than leaving the absolute number (a "weakened" stage would otherwise leave a character disproportionately tanky) or fully healing (a free heal an evolution shouldn't grant outright). `changes.tags` and `changes.energyCostOverrides` aren't applied to runtime state yet — nothing reads a per-character tag list or cost override today (logged as OQ-33).
10. **RNG manipulation as a one-shot queued modifier, consumed by the next `randomOutcome` roll** (`rng-modifiers.ts`, `ActiveStatus`-adjacent `RngModifier` on `CharacterRuntimeState.pendingRngModifiers`): spec/01 names four manipulations — force outcome, guarantee min/max, reroll, weight modification — all "implemented as modifiers on RandomOutcome" per phase-03-advanced-systems.md. Since a `RandomOutcome` branch carries only a weight (no inherent numeric value), "min"/"max" are read as author-order convention: branches are listed worst to best, and `guaranteeMin`/`guaranteeMax` pick the first/last. `weightBoost` multiplies the last branch's weight by a caller-given multiplier (biasing without guaranteeing); `reroll` draws twice and keeps the second. `forceOutcome` picks an exact index.
11. **`ActiveStatus` gains a generic `param?: string`**, resolving OQ-29's Ability Lock/Energy Lock blocker: Ability Lock's `param` is the specific locked ability id (checked in `actions.ts`'s `validateAction`); Energy Lock's is the locked `EnergyFamily` name (also `validateAction`, blocking any ability whose *effective* cost needs that family). Energy Cost Increase needed no such parameter — it just adds its magnitude onto NEUTRAL cost (`getEffectiveCost`, `actions.ts`), the one component any family can pay. All three move from OQ-29's deferred list to implemented; Resurrection Lock (checked in the `resurrect` effect) does too, since building resurrection this phase made it nearly free.
12. **`hasTag` and `secretScript` conditions still always return `false`** (`conditions.ts`): tags live on `CharacterDefinition`, which no engine runtime references yet (no roster exists before Phase 04); no secret script is registered in this file's own registry below. Both are honestly false rather than silently wrong — logged as OQ-31 alongside the other conditions-system gaps.
**Consequences:** Every one of phase-03-advanced-systems.md's eleven acceptance-criteria items has a passing, purpose-built test (`triggers.test.ts`, `snapshot.test.ts`, `rng-modifiers.test.ts`, plus additions to `damage.test.ts`, `effects.test.ts`, and `resolver.test.ts`) — 179 tests total, up from 124. `onMatchStart` is defined in the schema but never fired by `createBattle` (no passives exist to react to it before a roster does); `onTurnStart`/`onTurnEnd` fire once per living character at the very start/end of `resolveTurn`, which is a reasonable interpretation but not the only possible one. Both logged as OQ-31.
